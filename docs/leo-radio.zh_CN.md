# LEO Radio 集成 — 2.0.2

第三个工牌小程序基于 [leo0183/leo-radio](https://github.com/leo0183/leo-radio)，参考提交 `e28b8adafb2ca95e386e8b6e7db0db042cf09523`。电台共用工牌 Wi-Fi、音频设备、游戏生命周期及五种主题颜色。木鱼和语音钥匙扣继续保留，24 个音效包 / 726 段精选音效与所有 Flash 分区地址不变。

## 使用

工牌首页 → OK → 小程序 → 城市电台。连接已保存的 Wi-Fi 后，根据网络位置查找电台并开始播放。本地结果与 57 个内置精选 MP3 频道合并并去重；本地查询失败时仍保留精选列表。这是网络电台；FM 刻度为视觉转盘，硬件不接收调频无线电信号。

| 操作 | 功能 |
| --- | --- |
| 上 / 下 | 上一个 / 下一个电台 |
| 短按 OK | 暂停 / 继续 |
| 长按上键 | 电台设置 |
| 长按下键 | 停止播放 |
| 长按 OK | 设置子页直接返回一层；根页面存在不同去向时选择小程序、工牌或继续 |

退出弹窗说明离开会停止播放；打开或取消弹窗本身不停止直播。入口只有工牌的快捷启动直接退出，不提供重复目的地。详见[按场景返回规则](setup-navigation.zh_CN.md)。

设置包含音量（0–100%，每次 5%）、自动定位或七个预设城市、15/30/60/90 分钟定时停止。上下选择，OK 确认。定时只停止电台，不关闭工牌。音量、城市及选中的电台保存在独立的 `badge_radio_v1` NVS 空间；退出会清除定时。音量调整立即生效，但设置写入会等到暂停、切台、退出等播放边界，不打断 PCM 供给；边界前突然断电，最近尚未保存的调整可能丢失。Wi-Fi 沿用现有 USB 或热点配置页，无需单独账户或电台网页。

背景、面板、刻度、音量振幅条、标题和文案跟随当前工牌主题，也支持自定义配色。全部小程序复用首页相同的顶部栏：AI Passport、已连接 Wi-Fi 图标、电量百分比及分隔线。Wi-Fi 配置仅保留在工牌系统设置中。动态条反映解码后 PCM 的实际振幅，不是频谱分析。未知频率的电台显示 NET，不虚构频率。

## 集成及内存

- `radio_app.cc` 接入游戏框架。UI 和刷新定时器在 LVGL 锁内操作，后台通过同步快照更新状态，不直接访问界面对象。
- 三个协作任务分离实时要求：优先级 5、10 KiB 栈的主任务执行目录查询、MP3 解码、单声道混音及振幅计算；优先级 4 的 HTTP 读取任务使用 6 KiB 栈和 8 KiB 压缩队列；优先级 6 的 PCM 输出任务使用 4 KiB 栈和 8 KiB PCM 队列。输出任务存活期间，只有它设置 codec 格式／音量并写入 PCM。解码、HTTP 等待、电量轮询和振幅计算均不在输出任务中执行。取消时先等待两个子任务结束，再释放缓冲、HTTP 和回调上下文；主任务停止后才删除屏幕。停止超时则保留页面供再次退出。
- 首次压缩数据预缓冲目标为 2 KiB，最多等待 500 ms，不再在每次换台时引入数秒启动等待。8 KiB 压缩容量在 64 kbit/s 下约为 1.0 秒，在 128 kbit/s 下约为 0.5 秒；这是为接收栈留出内存的有界容量，更长的数据投递停顿仍可能缓冲。PCM 输出首次等待 4 KiB 或最多 100 ms，随后每次最多输送 320 个采样。两个队列在暂时断供后都不会重新触发满额等待。普通 HTTP 正文读取默认使用有界的 256 字节请求，退出／重新进入应用后也保持该默认；1024 字节仅保留为显式诊断对照。至少 100 ms 没有真实 PCM 输出才显示缓冲状态。直播连接／播放期间请求 `WIFI_PS_NONE`，在当前流结束时释放。
- 锁定 `espressif/esp_audio_codec` 2.5.0，仅注册 MP3 解码器。解码输出缓存保持 4,608 字节（一个最大立体声 MP3 帧），输入窗口为 4 KiB。未消费的压缩数据保留到后续读取，支持输出缓存而不消费新输入。不支持的格式、非法 PCM 对齐或填满输入窗口仍无进展时正常报错退出。保留原生采样率、16 位精度及单声道混音。只在开始、断流／恢复和停止时应用五毫秒的整数音量斜坡；这些过渡之外的普通采样保持不变，不用滤波掩盖解码杂音。
- `radio_buffer_budget.h` 集中定义应用缓冲预算：8 KiB 压缩、8 KiB PCM、4 KiB 解码输入和 4,608 字节解码输出，合计 24.5 KiB，另计控制对象和 20 KiB 任务栈；解码器、TLS、lwIP 及显示分配不包含在内。编译期 25 KiB 应用缓冲上限用于防止无意吃掉接收余量。32 KiB 压缩缓冲试验在 MP3／输出任务延迟分配完成后只剩约 4–8 KiB 空闲堆，已撤回；不能只按解码前的余量做预算。当前配置相对该试验归还 24 KiB，并保留独立 PCM 输出。子任务停止后释放所有流资源，分配失败正常退出。BSP 共用 I2S／DMA 参数和其他音频应用不变；堆、最大连续块、输出栈及长期稳定性仍须实机验收。
- 长时间直播循环在媒体入队时更新音频活动时间。不能仅因外层电源检查尚未执行，就在换台时把刚刚播放的 codec 错判为已空闲 15 秒。
- 目录响应按最多 4 KB 的单条对象拆分、解析，限制总字节数和请求时长，跳过超大条目，不在内存中保留完整目录树。
- 木鱼 4,480 字节音色缓存和语音钥匙扣 3,420 字节包/PCM 缓存改为游戏运行时分配，任务停止后释放，避免无 PSRAM 的 ESP32-C3 常驻存放未使用的游戏缓存。
- 不启动原项目独立的 Wi-Fi 管理器、电源控制器或视频彩蛋；网络配置、休眠与返回导航由工牌管理。

## 验证及安装

`./tools/validate.sh --static` 覆盖频率解析、单声道转换、定时边界、分层导航、分段／超大 JSON 对象、并发队列完整性／背压／回绕、有界压缩／PCM 储备模型、未消费解码输入，以及使用模拟 BSP／RTOS 的真实 PCM 输出模块。输出模块测试覆盖 codec 单任务所有权、生产延迟、有符号音量斜坡边界、普通 PCM 逐位不变、短流结束排空、断流／恢复、音量、格式／任务创建／写入失败及取消／退出握手。状态桥测试比对诊断中的缓冲／播放状态与真实状态持有者，电源持有者测试覆盖长时间直播不返回外层电源检查时的媒体活动更新。主机模拟不代表音质或目标设备时序验收。直播结束日志报告重新缓冲次数，以及上次真实媒体 PCM 写入完成到下次写入开始的最长间隔。这些计数只供诊断，不代表音质验收。只读协议请求 `{"id":1,"op":"radio_info"}` 可通过已有 USB／热点通道读取版本 4 播放计数，不依赖串口日志送达；维护计数本身不分配内存。查询不亮屏、不修改设置、不暴露电台 URL。`session` 在每次直播尝试时变化；`active`、`httpBytes`、`httpReads`、`httpTimeouts`、`maxHttpUs`、`queuedBytes`、`pcmFrames`、`pcmBytes`、`sampleRate`、`channels`、`rebufferEvents`、`maxFeedGapUs` 和 `maxDecodeUs` 描述该次直播。版本 2 新增 `pcmQueuedBytes`、`pcmUnderruns`、`minFreeHeap`（采样得到的最小值，尚未观测时为零）和 `writerStackFree`（最小剩余字节数，输出任务结束时公布）。版本 3 还报告当前 `heapFree`、`heapLargest` 和状态持有者的真实 `playbackState`（0 停止、1 连接中、2 缓冲、3 播放、4 重连、5 错误），以区分真实断供与未更新的显示文字。`queuedBytes` 表示压缩储备，`pcmQueuedBytes` 表示解码后的储备。`pcmFrames` 是成功写入真实媒体的 BSP 数据块次数，不是 MP3 帧数；斜坡／静音不计入 PCM 字节、数据块及媒体供数间隔。计数不是测量到的扬声器输出。暂停后保留计数；各字段为独立原子观测，不是事务快照。`error` 为 0 表示尚未报告错误，1 为 HTTP 打开／状态错误，2 为 HTTP 读取错误，3 为 HTTP 空闲八秒，4 为分配失败，5 为解码错误，6 为格式错误，7 为 PCM 输出失败，8 为输入窗口无进展，9 为启动超时。响应同时报告 Wi-Fi 连通状态和实际 modem sleep 模式。版本 4 增加 `probeMode`（0 播放、1 预热、2 只接收并丢弃）、实际 `readBytes`、`probeDrainedBytes`、`waitingForSpace`、`maxSpaceWaitUs`、`timeoutSocketReady`、`socketReadyChecks`、`peerFamily`、按主机序打包的 `peerIp4`、可选 IPv4 `peerAddress` 和 `tls`。超时后立刻发现 socket 可读，也可能只是两次检查之间新包刚刚到达，不能单独作为客户端出错的证据；须比对有效可读性检查次数、连续观测、内存和对端地址。实机须检查 32／44.1／48 kHz 电台、弱 Wi-Fi、调音量、暂停恢复、快速切台、反复退出、栈／堆余量，并在低音量和常用音量下试听爆音。`python3 tools/render_radio_host.py` 用实际生产 LVGL 界面渲染四套预设主题和五种页面，并在相同 40 KB LVGL 内存池下循环创建/销毁 100 次。

### 有界 USB 接收对照

这些是主动诊断，**不是**只读查询，也不代表缓冲已经修复。命令不接受 URL，只操作已经初始化、联网、暂停并完成流清理的电台应用中当前选中的频道：

- `{"id":2,"op":"radio_receive_probe","seconds":20,"readBytes":1024}` 排入一个接收对照；`seconds` 必须为 5–20，`readBytes` 只能为 256 或 1024。主任务预热八个 MP3 帧及真实 codec／PCM 输出分配，但不入队媒体；随后保留这些分配，让同一优先级 4 的 HTTP 读取任务接收并丢弃数据，不持续解码、输出，也不受应用队列背压影响。计时从预热完成后开始；后续延迟分配和 TCP 占用仍可能不同，须核对实测堆余量。界面显示 `RX TEST`，不播放或录制解码后的节目；完成后仍暂停。网络中断、定时到期、改变流代次的按键及退出应用会取消对照。
- `{"id":3,"op":"radio_read_size","readBytes":256}` 为下一次普通直播选择临时读取粒度，仅在暂停／空闲且未保留自测请求时接受。只支持 256 和 1024，普通默认现为 256，退出／重新进入后恢复该默认。这样可在不修改凭据、保存设置及共用 Wi-Fi 配置的情况下做读取粒度 A/B 测试。

两条命令都只允许 USB，且只投递非阻塞请求；参数错误或忙碌时不会另起任务或直播。`radio_info` 提供 `probeAllowed`、`probeBusy` 和 `nextReadBytes`。请求入队不保证执行：持有者取走之前若导航／网络状态变化，请求可能取消。主机测试覆盖自测准入／保留、取消、队列丢弃及已分配但未喂入媒体的 PCM 输出。它们用于隔离假设，任何单个结果都不能直接证明外部网络有故障。

### 实时供数分离的测量依据

在独立输出任务引入之前，44.1 kHz 会话记录到约 13.1 ms 的解码峰值和约 37.6 ms 的媒体供数间隔，而抽样时压缩队列经常仍有数据。共用的四个 160 帧 DMA 缓冲在 44.1 kHz 下合计最多约 14.5 ms，写入完成后的可用余量更小。另一些抽样区间连续数秒没有 HTTP 进展，媒体空档达到 1.26 秒和 3.03 秒；Wi-Fi 仍保持关联，模式为 `WIFI_PS_NONE`。这些观测支持把解码与 PCM 供给分离，但后续 32 KiB 压缩储备试验只剩 4–8 KiB 空闲堆。接收端内存紧张时发生 HTTP 超时，不能据此判定是外部网络故障。有界的 8 KiB 配置归还接收余量并缩短启动等待；仍需实机对比，不能据此宣称全部噼啪声或停顿已经消除。后续缩减预算的实机测试中，最小空闲堆仍有约 30 KiB、最大连续块约 25 KiB，却仍记录到压缩／PCM 队列清空和数秒读取超时。电脑直连同一电台 URL，使用 5,760 字节 socket 接收缓冲、8 KiB 应用队列并按媒体速率消费，连续 20 秒没有断供，最长读取约 265 ms。调查范围因此收敛到设备接收／流控／负载或不同对端／路径，而不是重复先前的内存假设。有界设备接收对照及对端地址记录用于区分这些情况。

目标设备的两组只接收对照（1024 字节与 256 字节请求）均在记录到的同一对端完成约 20 秒测试，各收到 225,386 字节（包含源端起始突发数据），每个抽样的一秒区间都有进展。随后临时选择 256 字节进行的普通播放持续约 117 秒，重新缓冲和 PCM 欠载均为零，最大媒体供数间隔为 3,575 us，抽样最小空闲堆为 30,500 字节。这是真实播放，不是隐藏提示或静默接收对照。继续观察同一会话至约 886 秒，计数出现一次重新缓冲／欠载，最大媒体空档为 539,825 us，抽样最小空闲堆为 26,556 字节。因此该配置显著减少了频繁停顿，但未通过严格的长时间零缓冲标准。该结果支持将 256 固化为构建默认，同时保留小内存预算和独立输出任务。但顺序进行的单次对照不能证明底层 TCP／Wi-Fi 的具体机制、全部频道可用性或长期稳定性。旧版已安装镜像在更新前仍会恢复到 1024；仅临时选择读取粒度不会跨退出／重启保存。原始日志须私密保存，目标设备对比确认之前，不能宣称缓冲或音质验收通过。

`-D BADGE_RADIO_DEVICE_PROBE=ON` 为可选台架测试，会注入导航事件。**正常固件必须设置 `-D BADGE_RADIO_DEVICE_PROBE=OFF`**，尤其是复用测试构建目录时。交付镜像关闭此选项。

从 1.9.1 更新使用分段写入引导、分区表和应用，音效分区无需改写。合并镜像用于空白设备；在已配置工牌上整包覆盖会改写包含用户数据的间隙。私有备份必须放在交付目录之外。

## 2.0.1 — 小程序、统一顶部与按键响应
